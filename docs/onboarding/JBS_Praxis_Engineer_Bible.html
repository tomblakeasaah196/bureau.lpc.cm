Who we are — the JBS standard

Before a single line of code, understand the bar you are being asked to clear. JBS Praxis builds real software that real businesses run their money and operations on. That fact shapes everything in this Bible.

What JBS Praxis does

We design and build production business systems — the software a company logs into every morning to run its operations. Two kinds dominate our work, and this Bible teaches you both:

  • ERPs (Enterprise Resource Planning systems) — the accounting, inventory, sales, HR, payroll and treasury brain of a business. Our reference ERP in this Bible is a live system: bureau.lpc.cm, a full accounting & distribution platform built to the West-African SYSCOHADA accounting standard.
  • Field-force / operational platforms — apps that people use out in the world: sales reps visiting pharmacies, drivers delivering stock, agents capturing leads offline. Our reference field system is the Fidson FieldForce Programme, a React PWA delivered milestone-by-milestone.
📌 The key insight

Almost every JBS project follows the same shape: a secure login, role-based access, a database with disciplined migrations, an API layer, a web/PWA front-end, a few heavy integrations (AI, email, payments, maps, push), documents (PDFs, e-signatures), and a repeatable way to deploy and support it. Learn the shape once, and you can build any of them.

The five non-negotiable values

1
Demonstrable — "if it can't be shown, it isn't done"
2
Secure by default, never as an afterthought
3
Auditable — every change traceable
4
Honest failure — never fake a value or hide an error
5
Full-stack ownership — you build it, you ship it, you support it

Value four has a story. On the real CRM dashboard, two headline numbers ("money owed", "empties owed") silently read 0 for months. The queries behind them referenced columns that did not exist — but each was wrapped in catch { $x = 0; }, which quietly turned a crash into a plausible-looking business fact. A company with no debt and a company whose debt query is broken looked identical on screen.

🛑 The rule that came out of it

Never let a catch block substitute a plausible business value. A number that cannot be computed must fail loudly or show "—" / "unavailable" — never a fake 0 that a human will trust. You will meet this rule again in the QA and code-review lessons. It is the soul of the JBS standard: we would rather show nothing than show a comfortable lie.

Who this Bible is for

You might be an amateur data engineer, a career-changer, or someone who has barely coded. That is fine — this Bible starts from "what is a server" and ends with "how to run a client go-live." What we ask of you is not prior knowledge. It is seriousness: the willingness to actually do the assignments, read the real code, and hold yourself to demonstrable work.

How software actually runs

If terms like "server", "request", "API" and "database" are fuzzy, this lesson fixes that permanently. Everything else in the Bible sits on this mental model, so go slowly.

The life of a click

Imagine a sales rep taps "Save visit" in the FieldForce app. Here is what actually happens, and it is the same story for every button in every system we build:

Figure 1 — the request / response cycle, the heartbeat of every web system
  1. The client (the rep's phone) packages the visit data and sends an HTTP request to a URL on the server — e.g. POST /api/v1/visits.
  2. The server receives it, checks who is asking (authentication) and whether they're allowed (authorization), validates the data, then talks to the database.
  3. The database stores the row and confirms.
  4. The server sends back a response — usually JSON — and the client updates the screen.
🔑 The single most important security fact

The client is untrusted. Anyone can fake a request from a phone or a script. That is why the server must re-check everything — permission, validation, ownership — on every write. "The button was hidden on the front-end" is never a security control. Burn this in; we will repeat it in the RBAC and security lessons because it is the source of most real-world breaches.

The one rule about secrets

🔑 Secrets never touch source code. Ever.

API keys, passwords, database credentials, tokens — these live in a .env file (or a secrets manager), and .env is git-ignored so it is never committed. What is committed is .env.example — a template with the names of the variables and blank values. On the ERP, the security checklist literally requires this command to return zero matches:

the "no secrets in code" trip-wirebash
# Must return NOTHING. A hit here blocks the merge.
git grep -E "(password|api_key|secret) *= *['\"]"

Here is the real ERP .env.example pattern — note the header comment that spells out the rule for the next engineer:

.env.example (excerpt, bureau.lpc.cm)ini

# Commit THIS file, NOT .env.

DB_HOST=localhost
DB_NAME=your_database_name
DB_USER=your_database_user
DB_PASS=your_database_password

# Master key that encrypts vendor API keys stored in the DB.
# Generate once with: openssl rand -base64 32
APP_ENCRYPTION_KEY=
💡 If you ever leak a secret

It happens to everyone once. The response is immediate: rotate the key (invalidate the old one and issue a new one) at the provider, then remove it from history. Do not "just delete the line and commit" — git remembers. Tell your lead. A leaked-and-rotated key is a non-event; a leaked-and-hidden key is an incident.

The bootstrap: one line that does everything

Every page and controller begins with the same first line. It guarantees that by the time your code runs, the environment, database, session, security headers, CSRF protection and permission engine are all loaded and warm. Read the real header comment — JBS code documents why, not just what:

every entry point starts like thisphp
<?php
// modules/crm/clients.php
require_once __DIR__ . '/../../includes/bootstrap.php';
Rbac::requirePermission('crm.clients.view');

// From here on: DB is connected, session is live, the user's
// permissions are loaded, security headers are already sent.

The bootstrap is idempotent — safe to include many times, it only runs once (a defined('LPC_BOOTSTRAPPED') guard returns early). It also enforces the session inactivity timeout and the "you must reset your password" gate. One file, loaded everywhere, means these rules cannot be forgotten on a new page.

💡 The pattern behind the pattern

Notice the shape: a shared foundation that every entry point is forced to go through. In Fastify you'd express this as a set of plugins and hooks that run before every route. Different words, identical idea: never let a developer accidentally skip security by forgetting to add it to a new page.

Databases from zero

Data is the point. The UI is just a window onto it. This lesson takes you from "what is a table" to reading real SQL, so the rest of the Bible makes sense.

Tables, rows, columns, keys

A relational database stores data in tables — think strict spreadsheets. Each row is one record; each column is one field with a fixed type. A primary key (usually id) uniquely identifies a row. A foreign key is a column that points at another table's primary key — that's how tables relate.

Figure 2 — two tables related by a foreign key

The four things you do to data (CRUD)

SQL basicssql
-- CREATE a row
INSERT INTO clients (name) VALUES ('Clinique Nord');

-- READ rows (with a relationship)
SELECT c.name, SUM(i.amount) AS total
FROM clients c
JOIN invoices i ON i.client_id = c.id
WHERE c.id = 12
GROUP BY c.name;

-- UPDATE a row
UPDATE clients SET name = 'Clinique du Nord' WHERE id = 13;

-- DELETE (rarely — we prefer a "soft delete": deleted_at = NOW())
UPDATE clients SET deleted_at = NOW() WHERE id = 14;
💡 Soft-delete, not hard-delete

At JBS, business records (clients, invoices, journal entries) are almost never truly deleted. We set a deleted_at timestamp and hide them. Why? Auditability. A distribution business needs to prove what happened last year. And a deleted client with unpaid invoices is a data-integrity disaster. On the ERP there's even a "corbeille" (trash) with a 30-day retention window before a nightly job purges for good.

Every JBS table follows the same recipe

This convention is written into the SQL rulebook. Every business table has:

  • id INT AUTO_INCREMENT PRIMARY KEY — the unique identifier
  • created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP — when it was made
  • updated_at + updated_by — when, and by whom, it was last changed
  • deleted_at TIMESTAMP NULL — the soft-delete marker
  • Every foreign key indexed, and declared ON DELETE RESTRICT (you can't delete a parent that still has children)
  • Money is always DECIMAL(15,2), never FLOAT — floats lose pennies, and in accounting that is unforgivable
✎ Knowledge check
Why is money stored as DECIMAL(15,2) and never FLOAT?
Floats can't represent decimal amounts exactly, so totals drift by fractions of a cent — fatal in accounting.
DECIMAL is faster to compute.
FLOAT can't store numbers above 1000.
It's just a style preference with no real effect.

Coding conventions & house style

Consistency is a feature. When every file looks like every other file, anyone can read anyone's code, and AI tools produce output that fits. These are the real house rules from the ERP's developer guide — learn them as law.

The rules that never bend

RuleWhy it exists
Every DB write uses a prepared statement — never string-interpolated SQL, even for integers.Prevents SQL injection, the #1 web vulnerability. No exceptions ever.
Never echo an exception message to the user. Log it server-side; return a generic message.Error text leaks table names, file paths and logic to attackers.
Escape all output: htmlspecialchars($v ?? '', ENT_QUOTES, 'UTF-8').Prevents XSS — a malicious value rendering as live HTML/JS.
Transactions wrap any multi-row write: begin, commit, rollback on error.Either all the rows change or none do — never a half-written state.
Type hints on new code: function foo(int $x): array.The computer catches type mistakes before your users do.
snake_case for DB & PHP variables; PascalCase for classes; camelCase for JS.Predictable names = readable code.
French UI strings, English code comments.The ERP's users are francophone; its engineers are bilingual. (Your comments & this Bible are English.)

Right vs. wrong — the injection trap

❌ Never — string interpolation

dangerousphp
// If $id is "1; DROP TABLE clients"…
$db->query("SELECT * FROM
  clients WHERE id = $id");

✅ Always — prepared statement

safephp
$stmt = $db->prepare(
  "SELECT * FROM clients
   WHERE id = ?");
$stmt->execute([$id]);

The value $id can never "escape" its slot and become SQL in the prepared version — the database treats it strictly as data. This one habit prevents an entire category of catastrophic breaches.

The JavaScript rules

  • Vanilla JS + Fetch on the ERP — no jQuery, no new libraries without discussion. (FieldForce uses React; same discipline, different tool.)
  • Render user data with textContent, never innerHTML += apiString. Building HTML from server strings is how XSS gets in.
  • Every fetch shows a loading state and handles errors — never a silent catch{}.
📌 "Files get one concern each"

If a page grows past ~800 lines, split it. One class = one job. This keeps files readable and makes them easy for both humans and AI to reason about. A 3,000-line file is a place bugs hide.

✎ Knowledge check
You need to fetch a client by an ID that came from the URL. You're "sure" it's a number. How do you query?
Interpolate it directly — it's just a number, so it's safe.
Use a prepared statement with a ? placeholder — always, no exceptions.

Documentation & config as data

This is the single idea that most separates a JBS system from an amateur one. Anything that a non-engineer might need to change — wording, help text, a sales proposal, who-can-see-what — lives in data, edited from a screen, not hard-coded and re-deployed.

Why "in code" is a trap

Suppose the help article for "How to create an invoice" is a block of text inside invoices.php. To fix a typo, an engineer must edit code, review it, and run the whole deploy pipeline. So typos never get fixed, and documentation "goes stale at the speed of the deploy pipeline." The fix: store it in the database, edit it from an admin page.

Figure 3 — move anything a non-engineer edits out of code and into data

Three real examples from the ERP

Sales proposal copy (every string, logo, share message)"Proposal Studio" — a template in the DBSales, with no code change

💡 The subtle security win

The Help Centre pushes this further: an article is gated by an existing module permission (e.g. crm.clients.view), never a parallel one. So an article is visible to exactly whoever can open the page it documents — "who may read this help" and "who may use this feature" cannot drift apart, because they are literally the same permission. Great architecture removes whole categories of future bugs.

How to recognise where to apply it

Ask: "Will a non-engineer ever want to change this without waiting for a deploy?" If yes — wording, prices, email templates, feature copy, business rules that change often — make it data. If no — core logic, security rules, the double-entry accounting engine — keep it in code where it can be reviewed and tested.

Why we build with AI

At JBS, AI coding tools are not a shortcut and not a crutch — they are how a small team ships production systems at eleven-milestones-in-eleven-weeks pace. But there is a hard rule: you must understand everything the AI writes. An engineer who ships code they cannot explain is not an engineer.

What changes, and what doesn't

✅ AI makes you faster at

  • Writing boilerplate (a new controller, a migration, a form)
  • Explaining unfamiliar code
  • Finding where a feature lives in a big codebase
  • Drafting tests and catching edge cases

❌ AI never replaces

  • Your judgement about whether the code is correct
  • Understanding why a design is right
  • Responsibility — you own what you ship
  • Security review — AI writes bugs too
  • Knowing the business problem
🛑 The JBS AI covenant

"I understand what I am doing, and I can audit and perfect my work." If you cannot read the diff the AI produced and explain each line to a colleague, you are not done — you are gambling. This covenant is the difference between an engineer who uses AI and an operator who copies output and prays.

The anatomy of a great prompt

A weak prompt gets weak code. A great prompt gets code that fits your codebase, respects your rules, and is easy to verify. There is a repeatable formula. Learn it and your output quality jumps overnight.

The five ingredients: C-T-C-E-F

C
Context
What system, which files, what conventions apply.
T
Task
The one specific thing you want done.
C
Constraints
The rules it must not break. Your non-negotiables.
E
Examples
Point at an existing pattern to copy.
F
Format
How you want the answer: a plan, a diff, one file.

Watch a prompt get better

🔴 WeakAVOID
add a way to delete clients

Too vague. It will guess at your patterns, probably skip permission checks, maybe hard-delete, and put the code who-knows-where.

🟢 Strong — C·T·C·E·FUSE THIS
Context: This is the bureau.lpc.cm PHP/MySQL ERP. API controllers live in api/v1/ and dispatch on $_POST['action']. Permissions are dot-notation and checked with Rbac::requirePermission. Task: Add a "soft_delete" action to api/v1/clients_controller.php that sets clients.deleted_at = NOW() for a given client_id. Constraints: Use a prepared statement. Require the permission 'crm.clients.delete'. Never hard-delete. Return generic JSON on error and log the real error server-side. Wrap the write in a transaction. Example: Follow the exact structure of the existing 'create' action in the same file. Format: First show me a short plan. After I approve, show the diff for just that one file.
✅ Why the strong prompt wins

It told the AI where the code goes, which rules matter, what pattern to copy, and how to deliver — so the result already fits your codebase and your standards. You spend your energy reviewing a good answer instead of fixing a bad one.

Six habits of high-signal prompts

  1. Name the files. "@api/v1/clients_controller.php" beats "the clients code."
  2. State your non-negotiables every time until they live in CLAUDE.md (next lesson): prepared statements, permission checks, no hard delete.
  3. Point at a pattern to copy. "Follow the existing 'create' action" anchors the style.
  4. Ask for a plan first on anything bigger than a one-liner. Approve the plan before code.
  5. Constrain the blast radius. "Only touch this one file." Small diffs are easy to review and easy to revert.
  6. Demand verifiability. "Show me how to test this." If you can't test it, you can't trust it.

Prompting patterns that ship

Beyond a single good prompt, there are workflows that consistently produce shippable code. These are the patterns JBS engineers run every day.

Pattern 1 — Plan → Approve → Build

Never let the AI free-build a feature. Make it think out loud first, correct the plan cheaply (words are cheaper than code), then let it execute.

💬 The plan-first openerWORKFLOW
Before writing any code: give me a step-by-step plan to add web-push notifications to this app. List every file you'll create or change and the DB migration needed. Flag any decision you need me to make. Wait for my approval.

Pattern 2 — Small diffs, one concern

A 12-file change is unreviewable and un-revertable. Break work into slices, each of which you can read, test, and commit on its own. "One feature = one branch; one migration = one file" is the JBS rhythm.

Pattern 3 — Test-anchored building

Ask for the test with the code — or first. A failing test that then passes is proof, not vibes.

💬 Test-anchoredWORKFLOW
Write a Vitest test that asserts the payroll compute() function returns net = gross - deductions for a known example, then implement compute() until the test passes. Show me the test first.

Pattern 4 — The reproduce-then-fix loop (debugging)

When something is broken, don't ask "fix the bug." Ask it to reproduce first — a bug you can't reproduce is a bug you can't prove you fixed.

💬 DebuggingWORKFLOW
The invoice total shows 0 for client 12. First, write a small script that reproduces the wrong result. Then find the root cause — don't patch symptoms. Explain the cause, propose a fix, and show the same script now returning the right number.

Pattern 5 — The adversarial self-review

Turn the AI on its own work. This catches an astonishing number of bugs before they reach a human reviewer.

💬 Self-reviewWORKFLOW
Review the change you just made as a hostile senior engineer. What would make CI reject this? Any missing permission check, unescaped output, un-parameterised query, or missing error handling? List issues, then fix them.
💡 Chain them together

A full JBS feature session often runs: Plan → Approve → Build in small diffs → Write tests → Adversarial self-review → Run the repo's real checks → You read every line → Commit. Each stage is a prompt. This is what "AI-assisted" actually looks like — disciplined, not magical.

Git is the time machine and the teamwork engine of software. It records every change, lets many people work at once without stepping on each other, and lets you undo anything. It is not optional knowledge — it is the floor.

The API layer

The API is the server's menu of things a client may ask for. Every request enters here, and every request is authenticated, authorised, validated, and answered in JSON. Get this layer right and the whole system is safe by construction.

The JBS controller pattern

On the ERP, one file per domain (api/v1/<domain>_controller.php) handles all the actions for that domain, dispatching on $_POST['action']. Here is the canonical shape — memorise it, because you'll write dozens:

api/v1/clients_controller.php (the pattern)php
<?php
require_once __DIR__ . '/../../includes/bootstrap.php';

header('Content-Type: application/json; charset=utf-8');
Rbac::requireAuth();                 // must be logged in at all

$action = $_POST['action'] ?? $_GET['action'] ?? '';

switch ($action) {
  case 'list':
    Rbac::requirePermission('crm.clients.view');
    // ...read + echo json_encode([...])
    break;

  case 'create':
    Rbac::requirePermission('crm.clients.create');
    Csrf::requireValid();          // state change → CSRF token required
    // ...validate, prepared INSERT inside a transaction...
    break;

  default:
    http_response_code(400);
    echo json_encode(['status'=>'error','message'=>'Unknown action']);
}

Read what this guarantees: auth first, then per-action permission, then CSRF on writes, then the work, and a uniform JSON shape out. Every controller is boringly identical — and boring is exactly what you want in security-critical code.

The same idea in the FieldForce stack

On a Fastify + Zod backend, the shape is the same, spelled differently. A Zod schema validates the request body before your handler runs; a pre-handler hook checks the permission; the handler returns typed JSON:

the same idea in TypeScript / Fastify + Zodts
const CreateClient = z.object({ name: z.string().min(2) });

app.post('/clients', {
  preHandler: requirePermission('crm.clients.create'),
  schema: { body: CreateClient },        // Zod validates before handler
}, async (req, reply) => {
  const { name } = req.body;              // already validated & typed
  const row = await db.insert(clients).values({ name }).returning();
  return reply.send({ status: 'ok', client: row[0] });
});
💡 One shape, two spellings

Validate → authorise → do the work → return uniform JSON. Whether it's a PHP switch on $_POST['action'] or a Fastify route with a Zod schema, that is the contract. Recognising the shared skeleton is what lets you move between JBS projects without friction.

The data layer & migrations

The database schema changes over a project's life — new tables, new columns, new rules. Migrations are how you evolve it safely, in order, on every machine and server, without anyone running SQL by hand. The ERP has 120 of them.

What a migration is

A migration is a numbered SQL file that makes one schema change. A runner applies them in order, records which have run, and never runs the same one twice. The result: your laptop, a teammate's laptop, and production all reach the exact same schema by replaying the same files.

migrations/ (real, abbreviated)text
000_init_schema_migrations.sql   # the tracking table itself
001_rbac_seed.sql                # permissions + default roles
004_double_entry_trigger.sql     # enforce debit = credit in the DB
098_ai_settings.sql              # encrypted AI keys table
119_retire_legacy_lpc_accounts.sql
# … 120 files, applied strictly in numeric order

The three laws of a JBS migration

  1. One file, numbered, one change. NNN_verb_noun.sql. Never edit a migration that has already run — the runner checksums applied files and refuses a changed one. Need another change? Write the next number.
  2. Idempotent. Safe to run twice. Use IF NOT EXISTS, INSERT ... ON DUPLICATE KEY UPDATE. A migration that fails halfway must be safe to re-run.
  3. Transactional + verified. Wrap writes in START TRANSACTION; ... COMMIT; and end with verification queries in a comment.

Here is the real idempotent idiom from the ERP — add a column only if it isn't already there:

idempotent column add (from migration 004)sql
SET @sql = (SELECT IF(COUNT(*)=0,
  "ALTER TABLE journal_entries ADD COLUMN status
     ENUM('draft','posted','reversed') NOT NULL DEFAULT 'draft'",
  'SELECT \"status exists\" AS info')
  FROM information_schema.columns
  WHERE table_schema=DATABASE()
    AND table_name='journal_entries' AND column_name='status');
PREPARE s FROM @sql; EXECUTE s; DEALLOCATE PREPARE s;
💡 The database can enforce business rules too

Migration 004 doesn't just add a column — it installs a trigger so the database itself rejects any journal entry where debits ≠ credits, and refuses to delete a "posted" entry (you must reverse it). Why in the database and not just the app? Because the app is not the only thing that can write to the database. The deepest guarantees live closest to the data.

The runner

You run php scripts/migrate.php and the database catches up. This is what makes deploys repeatable.

Authentication — who are you?

Authentication answers "who is this?". It is the front door of the system, and front doors are where attacks concentrate. This lesson covers passwords, sessions, and a real account-takeover bug that teaches the deepest lesson of all.

Passwords are never stored — only hashes

You never store a password. You store a one-way hash (via bcrypt) — you can check a password against it, but you can't reverse it back to the password. On the ERP, one file, password_policy.php, defines the single rule set for the whole app: lpc_password_check() to validate, lpc_password_hash() to hash. Never call the raw hash function directly, and never re-inline the rules — one policy, one place.

💡 Why "one policy, one place" is load-bearing

Before this was centralised, three different screens (login-adjacent change, admin user creation, employee onboarding) each had their own copy of the password rules — and they drifted. The published browser checklist is even generated from the same rules, so the on-screen requirements cannot disagree with what the server enforces. Duplication of a rule is a future bug with a delay timer.

Sessions — staying logged in

After login, the server issues a session so the user doesn't re-enter their password on every click. JBS hardens sessions in the bootstrap: secure, http-only, same-site cookies; a server-side inactivity timeout; and a stored session token hash so a session can be revoked. When a user changes their password, their other sessions are revoked — a stolen session dies the moment the real owner re-secures the account.

The account-takeover bug — a permanent lesson

The password-change endpoint once had this guard:

the WRONG guardphp
// WRONG — a no-op for a caller with NO session at all
if (!empty($_SESSION['user_id']) && ...mismatch...) { reject; }

Read it slowly. If there is no session at all, the whole if is skipped — so an anonymous POST that merely knew an email and a current password could change the password and lock out the real owner. It was found by probing the live endpoint during a security audit, not by reading the code. The fix requires an authenticated session and that the session owner is the account being changed — both halves load-bearing.

🛑 The lesson

A security check that only runs "if a session exists" does nothing to a caller with no session — which is exactly the attacker you're worried about. And identical error messages ("Identifiants incorrects.") are returned for wrong-password, unknown-address, and locked-account, so an attacker can't enumerate which emails are real accounts. Small wording choices are security decisions.

Authorization — RBAC deep dive

Authentication asks "who are you?"; authorization asks "what are you allowed to do?". JBS uses RBAC — Role-Based Access Control. Master this; it appears in every project and it is where sloppy code becomes a breach.

The model: users → roles → permissions

A user has one role (admin, accountant, operations, driver…). A role holds a set of permissions, each a dot-notation key: <module>.<entity>.<action>. On login, the user's full permission set is loaded once and cached in the session; every later request reads the cache.

Figure 5 — one user → one role → many permissions

Gating, at every layer

LayerHow you gate it
Module pageRbac::requirePermission('crm.clients.view') at the top — unauthorised users get a 403 or a redirect.
API actionRbac::requirePermission('crm.clients.create') before the write (returns 403 JSON).
A button (server)if (Rbac::hasPermission(...)) { echo the button } — it isn't rendered at all.

🛑 The one rule that makes RBAC real

  1. Add the key to the permission catalog (permissions.php) so it appears on the Roles admin screen.
  2. Add an idempotent INSERT in a new migration (with ON DUPLICATE KEY UPDATE) — the catalog lists it, but the migration is what actually grants it.
  3. Grant it to the right roles (in the same migration).
  4. Use it: Rbac::requirePermission('module.entity.action') in code; data-perm in HTML.

Rendering data safely

The front-end displays data that ultimately came from users. If you render it carelessly, a malicious value becomes running code in someone else's browser — that's Cross-Site Scripting (XSS). Safe rendering is a habit, not a feature.

The attack, in one line

Suppose a client's name is saved as <script>steal()</script>. If your page builds HTML like list.innerHTML += name, that script runs in the browser of every user who views the list — it can steal sessions, submit forms, anything. The value "escaped its slot" and became code, exactly like SQL injection but in the browser.

❌ Never

XSS waiting to happenjs
row.innerHTML +=
  "<td>" + client.name + "</td>";

✅ Always

safe by defaultjs
const td = document.createElement("td");
td.textContent = client.name; // escaped
row.appendChild(td);

textContent treats the value strictly as text — angle brackets show as characters, never tags. The JBS rule is blunt: never build markup with innerHTML += from API-derived strings. The ERP even provides an auto-escaping tagged template (LPC.html\`...\`) so that every interpolated value is escaped automatically, and a deliberate LPC.raw() escape hatch so code review can find every place raw HTML was intentionally used. On the server side, the equivalent is htmlspecialchars($v ?? '', ENT_QUOTES, 'UTF-8') on every echoed value.

💡 Escaping is context-sensitive

HTML context → HTML-escape. JavaScript context (embedding data in a <script>) → json_encode(), not HTML-escaping. URL context → URL-encode. Using the wrong escaper for the context is itself a bug. The ERP loads PHP-generated data into a <script type="application/json"> block and parses it in JS — a clean, safe hand-off that avoids mixing code and data.

✎ Knowledge check
You're displaying a user-submitted comment in a list. Safest approach?
Concatenate it into innerHTML — it's just a comment.
Set it via textContent (or an auto-escaping template) so any tags render as harmless text.
Trust that users won't be malicious.
Strip spaces and hope.

LLM integration II — RAG & grounding

An LLM on its own will confidently invent answers about your business — it has never seen your data. The fix is RAG: Retrieval-Augmented Generation. You retrieve your own relevant documents first, then ask the model to answer only from them. This is exactly how the ERP's help assistant works, and it's one of the most valuable patterns you'll learn.

The idea

Figure 7 — retrieve first, then generate: the model answers only from your material

Embeddings — turning text into searchable meaning

To find the relevant documents, you convert each chunk of your docs into an embedding — a list of numbers capturing its meaning. You embed the user's question the same way, then find the chunks whose numbers are "closest" (cosine similarity). This finds text by meaning, not just keyword match. On the ERP, embeddings are computed by a nightly reindex job (a separate provider from the chat model, because "DeepSeek has no embeddings endpoint") and stored for fast lookup.

The pipeline — and why its order is a security design

Study the real help-assistant pipeline; every step is deliberate:

  1. Auth + rate limit — before anything that costs money.
  2. Retrieve — embed the question, rank chunks, and filter every candidate through the permission check so that by the time the controller sees a chunk, it is already something this user is allowed to read.
  3. Zero matches → a canned "not found", with no LLM call. Calling the model with no grounding just invites it to guess.
  4. Generate — the model answers using only the retrieved excerpts (enforced by the system prompt).
  5. Citations are built from the retrieved chunks the server already knows — never parsed from the model's own text. "Asking an LLM not to hallucinate a URL is a request, not a guarantee," so the citation list never comes from the model's output.
  6. Log every question — the raw material for "what can't our assistant answer yet?".
🛑 The grounding rules that keep AI honest
  • Answer only from retrieved context. No context → no answer. Never let it free-associate about your business.
  • Never trust the model for facts you can control. Links, permissions, prices — the server supplies those from real data; the model only writes prose.
  • Filter by permission before retrieval reaches the model — so the assistant can never quote a document the user isn't cleared to read.
  • "Not configured" and "nothing found" are not errors — they return a clean message the UI shows inline. Degrade, don't crash.

Secrets & encrypted storage

You've met the rule "secrets live in .env." But sometimes a secret genuinely needs to live in the database — and then you must encrypt it. This lesson teaches the JBS pattern for handling that trade-off without downgrading your security.

The dilemma

You want admins to rotate the AI vendor key from a settings screen — no deploy, no engineer. That means the key must live in the database. But a plaintext key in a MySQL column is a downgrade from .env: it lands in every nightly mysqldump backup. So you encrypt it at rest, with one master key that stays in .env.

the pattern (from Crypto.php)text
Algorithm:  AES-256-GCM  (authenticated encryption)
Master key: APP_ENCRYPTION_KEY in .env  (generated once, ~never rotated)
Stored as:  "v1:" + base64(IV + auth-tag + ciphertext)

encrypt()  → THROWS if the master key is missing
             (silently storing plaintext would be far worse than a 500)
decrypt()  → returns null on a bad/tampered row
             (one corrupt row must not take down the whole settings screen)

Why each choice matters

  • Authenticated encryption (GCM) — a row tampered with in the database fails to decrypt loudly, instead of returning silently-wrong bytes that get sent to an API as a "key." Corruption becomes a visible error, not a mystery bug.
  • The master key stays in .env — and that's not a contradiction. A 32-byte master key that's generated once and essentially never rotated is infrastructure, the same tier as the DB password. What you moved to the DB was the thing that changes when you switch vendors or plans. Match each secret's home to how often it changes.
  • The version prefix (v1:) — a cheap escape hatch so if you ever change ciphers, decryption can dispatch on the prefix instead of guessing.
💡 Fail loud on write, fail soft on read

Notice the asymmetry: encrypt() throws (never silently store a plaintext secret), but decrypt() degrades to null (one bad row shouldn't crash the whole settings page). This "fail loud where silence is dangerous, fail soft where a crash is disproportionate" judgement is everywhere in good JBS code — it's the mature cousin of "honest failure."

Systems send mail: password resets, notifications, reports. SMTP is the protocol for sending it. This lesson covers wiring it up — and a hard lesson about what happens when you build a feature that silently depends on mail that was never configured.

SMTP configuration — it's all in .env

🛑 The war story: "the reset that delivered nothing for months"

On the ERP, SMTP was never configured. MAIL_FROM was unset, and Mail::send() returned true while only writing to the error log. So the "Forgot password?" screen looked like it worked — it showed a success message — and delivered nothing, for months. 💡 The lessons
  • A function that returns true without doing the thing is a lie in your codebase. If mail isn't configured, send() should make that visible — not silently succeed.
  • Never make a critical flow (like account recovery) depend on a channel you haven't proven works. Have a fallback: admin-set passwords when there's no mail.
  • Feature-flag anything not ready. The email-reset machinery still exists, switched off, with an honest "disabled" message — ready to enable the day SMTP is real.

Deliverability basics

Getting mail to arrive (not land in spam) is its own craft: set up SPF, DKIM and DMARC DNS records for your sending domain, use a reputable provider, and monitor bounces. On client projects, email sending is often a pass-through cost the client provisions — the same rule as push: if it isn't provisioned, you flag it, you don't route it through a personal account.

The testing pyramid

Tests are how you prove — to yourself, your reviewer, and your future self — that the code does what you claim. "It works on my machine" is not proof. A test that fails, then passes, is proof. This is the backbone of "if it cannot be demonstrated, it is not complete."

Three levels, in the right proportion

Figure 8 — many fast unit tests, some integration tests, a few end-to-end tests
LevelWhat it testsExample
UnitOne function in isolation. Fast, many."payroll compute() returns net = gross − deductions"
IntegrationSeveral parts together, often with a real database."POST /clients actually inserts a row and enforces the permission"
End-to-end (E2E)The whole app through the UI, as a user."log in, create an invoice, download the PDF"

What makes a good test

  • It has a clear name that states the expected behaviour.
  • It follows Arrange → Act → Assert: set up the situation, do the thing, check the result.
  • It tests behaviour, not implementation — so it survives a refactor.
  • It covers the edge cases — zero, negative, empty, the boundary, the error path — not just the happy path.
  • It is deterministic — same result every run, no random flakiness.
💡 The most valuable test is the one for the bug you just fixed

Every time you fix a bug, add a test that would have caught it. That test is a permanent guard: the bug can never silently come back. A codebase's test suite is, in large part, a museum of every mistake the team has already made once and refuses to make twice.

Writing tests

Now the mechanics. You'll write a Vitest unit test (the FieldForce stack) and see the lightweight checks the ERP runs (lint + smoke tests). The tooling differs; the discipline is identical.

A Vitest unit test

payroll.test.tsts
import { describe, it, expect } from "vitest";
import { computeNet } from "./payroll";

describe("computeNet", () => {
  it("returns gross minus deductions", () => {
    // Arrange
    const gross = 500000, deductions = 120000;
    // Act
    const net = computeNet(gross, deductions);
    // Assert
    expect(net).toBe(380000);
  });

  it("never returns a negative net", () => {
    expect(computeNet(100, 999999)).toBeGreaterThanOrEqual(0);
  });
});

Run it with npx vitest. Red (fail) → write code → green (pass). That loop is the heartbeat of test-driven development.

Integration tests with disposable databases

FieldForce mandates "Vitest with disposable container databases." The idea (testcontainers): before the test run, spin up a real PostgreSQL in a throwaway Docker container; run migrations into it; run your integration tests against a real database; then destroy it. You get the fidelity of a real database with the cleanliness of a fresh one every time — no shared test database that slowly fills with junk and makes tests flaky.

The ERP's lightweight checks

Not every project has a heavy test suite from day one. The ERP leans on cheap, high-value checks that run on every deploy:

  • Lint everything: php -l on every changed file catches syntax errors before they ship. "php -l every file you touched" is in the pre-push checklist.
  • Smoke tests: verify.sh curls key pages as each role and confirms no 500 error — a fast "is the site standing up?" check.
  • Books-balance queries: for the accounting engine, SQL that asserts the general ledger actually balances.
  • Manual role walk-through: load affected pages as each of the four roles and confirm the gates work.
💡 A flaky test is worse than no test

The ERP once had smoke tests that failed on every run for a benign reason — and a "known-benign failure" trains everyone to ignore red. That's poison: once people ignore one red, they ignore all red. The fix was to make the check pass cleanly (skip-with-warning when test users aren't configured) so that any red from then on is a real problem. Keep your signal clean: green means green, red means stop.

Regression & release gates

A regression is when a change breaks something that used to work. A gate is a checkpoint that code must pass before it advances. Together they're how a fast-moving team ships weekly without the product quietly falling apart behind it.

Regression: the silent killer

You fix invoice totals; a week later, someone reports the dashboard is wrong — because your fix changed a shared query. That's a regression. Defences, in order of strength:

  • Automated tests that run on every change and re-prove old behaviour still holds.
  • A regression checklist in QA: the critical flows you re-verify before every release.
  • Small, isolated changes — a minimal diff can only break so much.
  • The bug-fix test rule from Lesson 1 — every past bug has a test standing guard.

Release gates — nothing advances unproven

Environments & secrets

The same code runs in different places — your laptop, a staging server, production — each with its own database, its own keys, its own settings. Keeping these cleanly separated is DevOps discipline #1, and it's where the .env file finally earns its keep.

The environments

productionReal users, real moneyThe real database, real keys, APP_DEBUG=false

Same code, different .env. That's the whole trick. The code reads its configuration — database, keys, feature flags — from the environment, never from hard-coded values. On the ERP, a tiny env() helper loads .env once and coerces types, and every setting flows through it.

🛑 The production .env lives only on production

It is never committed, never emailed, never in chat. On the ERP, the deploy explicitly preserves the server's .env across deploys — a git reset --hard never touches it because it's git-ignored. When you onboard, someone gives you access to set the production secrets through a secure channel; you don't get them pasted to you. Treat the production .env as the crown jewels, because it is.

Debug flags are environment-driven

Detailed errors on screen are a gift in development and a security hole in production (they leak file paths, queries, logic). So display_errors is never hard-coded — it's driven by APP_DEBUG, which is true locally and false in production. The same code, safe in both places, because the environment decides.

The deploy pipeline

Deploying is the act of getting your new code running for real users. It must be repeatable, scripted, and safe — never a human copying files by hand. Let's walk the ERP's real, live pipeline end to end.

The flow

the real deploy flowtext
   [ your machine — edit + commit ]
              │  push
              ▼
   [ GitHub — branch main, reviewed PRs merged ]
              │  on the server, run:
              ▼
   cd ~/public_html/bureau.lpc.cm
   git fetch origin main

What deploy.sh does, in order

  1. Sanity checks — right directory? PHP + database present? Is the built CSS real, not a placeholder stub?
  2. Preserve .env — keep the production secrets that live only on the server.
  3. Ensure directories & permissions — log dir, upload subdirs, correct modes.
  4. Run pending migrations — migrate.php applies new SQL files in order, tracked and checksummed.
  5. Lock permissions — chmod 600 .env, restrict includes/ and uploads/.
  6. Warm the cache — so the first real user doesn't pay the cold-start cost.
  7. Smoke tests — curl key pages; confirm no 500s.
  8. Print a PASS/FAIL summary — a clear green light, or a red stop.
💡 The build happens on the dev machine, not the server

🛑 Deploying is pulling the canonical state — never hand-editing

The one sanctioned way to change production is: push to GitHub, then on the server pull that exact state and run the deploy script. Never SSH in and edit a file by hand — that creates a production that no longer matches git, and the next deploy silently erases your fix (or worse, it doesn't, and now nobody knows what's actually running). CI/CD with GitHub Actions

CI (Continuous Integration) runs your checks automatically on every push, so broken code is caught in minutes, not in production. CD (Continuous Delivery/Deployment) extends that to automatically shipping code that passes. GitHub Actions is how JBS wires this up.

A CI workflow

A workflow is a YAML file in .github/workflows/. This one runs lint and tests on every pull request — the automated half of your PR gate:

.github/workflows/ci.ymlyaml
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "20" }
      - run: npm ci
      - run: npm run lint
      - run: npm test          # red here blocks the merge

Now every PR shows a green tick or a red cross automatically. Combined with branch protection ("CI must pass to merge"), broken code cannot reach main.

💡 CD is a goal, not always a given

Full auto-deploy is ideal, but real infrastructure sometimes blocks it. The ERP has a deploy workflow, but the host's firewall blocks the runner from reaching the server — so the deploy step stays manual (pull + deploy.sh on the server) while CI still runs on every push. The lesson: automate what you can, script the rest so it's still repeatable, and be honest in your docs about what is and isn't automated. A half-automated pipeline you understand beats a "fully automated" one you're wrong about.

Secrets in CI

CI sometimes needs credentials (to run integration tests, to deploy). These go in the repository's encrypted secrets settings on GitHub — never in the YAML file, which is committed. The workflow references them as ${{ secrets.NAME }}. Same principle as .env: the secret's name is in the code; its value is stored securely elsewhere.

Cron, backups, rollback & monitoring

Shipping is the start, not the end. A live system needs scheduled jobs, backups you've actually tested, a way to undo a bad deploy, and eyes on its health. This is the difference between "it launched" and "it runs."

Cron — scheduled work

A cron job runs a script on a schedule. The ERP uses them to purge soft-deleted clients after their retention window, archive old notifications and audit logs, and run nightly maintenance. Rule of thumb: anything that must happen "every night" or "every hour" without a human is a cron job. Keep them idempotent and logged — a cron that fails silently is a time bomb.

Backups — and the test that matters

The ERP backs up before risky operations: a tar of the files and a mysqldump of the database into a ~/backups/ folder. But a backup you've never restored is a hope, not a backup.

🛑 An untested backup is not a backup

The only way to know your backup works is to restore it — into a scratch environment — and confirm the data is intact. Teams discover their backups were broken at the exact moment they need them, which is the worst possible time. Schedule a restore drill. Do it before you need it.

Rollback — undo a bad deploy fast

When a deploy goes wrong, you need to get back to the last good state in minutes, not hours. Because deploys are just "the exact git state + migrations," rollback is well-defined: restore the previous code (git can check out the last good commit) and, if a migration caused it, restore the pre-deploy database backup. The ERP ships a rollback.sh that restores the latest backup with a confirmation prompt. Have the rollback ready before you deploy, not after it breaks.

Monitoring — know before your users tell you

  • Error logs — the ERP has a file-tail error monitor with its own admin page, so recent errors are visible without SSH. Errors go to a log outside the web root, never to the screen.
  • Uptime checks — something that pings the site and alerts you if it's down.
  • Health signals — for the ERP, "do the books balance?" queries; for a field app, "are visits syncing?".

The goal: you find out about a problem before the client does. A monitored system that pages you at 2am is healthier than an unmonitored one that lets the client discover the outage at 9am.

Running a demo

The demo is where your month of work either lands or fumbles. A great demo isn't about slick showmanship — it's about proving, calmly and clearly, that the promised thing works, on real data, in front of the people who decide.

Before the demo

  • Rehearse the exact walkthrough — the ERP describes "the walkthrough we run" for each milestone. Know every click.
  • Use real accounts and real data — a demo on fake data invites "but will it work with ours?". Pre-empt it.
  • Prepare the environment — stable connection, the right browser, seeded data, a backup plan if something's offline.
  • Prove each client structure — for FieldForce, mobile and desktop and manager web, each shown feeling purpose-built for its device.
  • Have your acceptance checklist open — demo against it, item by item, so acceptance is obvious.

During the demo

  • Tell the story, not the tech. "A rep arrives at a pharmacy with no signal and logs a visit" beats "we call the IndexedDB API." Speak the client's language.
  • Show, then explain. Do the action, let them see the result, then a sentence of what happened.
  • Narrate the value — connect each feature to the client's problem it solves.
🛑 When something breaks live (it will, eventually)

Stay calm and honest. Never fake it, never pretend a bug is a feature. "That's a defect — I'll log it and have a fix in the next build" earns more trust than a flustered cover-up. Clients forgive bugs; they don't forgive being misled. Honesty in a demo is the same value as honest failure in code.

💡 The demo is the acceptance test

Structure the demo as a live run of the acceptance criteria. When the last checkbox is ticked in front of the client, acceptance isn't a negotiation — it's a formality, because everyone just watched every item work. That's the whole point of baselining criteria up front.

Hypercare & support

The riskiest moment in a system's life is right after go-live, when real users hit it for the first time in ways you never imagined. Hypercare is the intense support period that carries a launch safely into steady state — FieldForce dedicates its entire final milestone to "National Rollout, Training & Hypercare."

Go-live is a plan, not an event

FieldForce reaches production through a deliberate ramp: field pilots during the build (milestones 2 and 6), then UAT & a pilot go-live (milestone 10), then national rollout with hypercare (milestone 11). You don't flip a switch for everyone at once — you prove it with a small group, learn, then widen. UAT (User Acceptance Testing) is the client's own users confirming it works for them before the whole company depends on it.

What hypercare looks like

  • Heightened monitoring — you're watching the logs and health signals closely, catching issues before users report them.
  • Fast response — a clear channel for users to report problems, and quick turnaround on real bugs.
  • Triage discipline — separate "the system is broken" (drop everything) from "I'd like it to also do X" (that's a change order, later).
  • A feedback loop — the questions users ask become new help articles; the bugs they hit become new tests.
💡 Every support ticket is data

The ERP logs every help-assistant question precisely so the team can later ask "what can't our assistant answer yet?". Apply the same mindset to all support: a recurring question is a gap in your help centre or your UX; a recurring bug is a missing test. Support isn't just firefighting — it's the highest-signal feedback you'll ever get about what your system actually needs.

🌟 The full circle

Notice how the whole Bible connects here: honest failure means bugs surface instead of hiding; monitoring means you see them first; tests mean fixes stay fixed; config-as-data means you improve help without a deploy; the milestone model means you ramped up safely. Hypercare is where every discipline you've learned pays off at once. This is what it means to own a system end to end.
